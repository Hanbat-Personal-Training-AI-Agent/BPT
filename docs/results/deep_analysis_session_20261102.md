# Deep-analysis service login lifetime — 2026-11-02

The service provider now watches `authSessionIdentityProvider` and captures an `AuthSessionLease`. Its token and refresh callbacks use that lease directly, without reading a disposed Riverpod Ref. Returning to the same uid in a new login, or replacing a notifier with the same uid, cannot revive the old service. Ordinary same-session profile updates and token refresh keep the current service usable.

An optional constructor predicate guards actual API/storage sends, late API responses, refresh/retry, queue reads/writes and returned downloads. Direct constructor callers without the predicate retain their existing behavior; the production provider supplies it. Queue writes also use the preferences-instance writer, with ownership rechecked when the queued write begins. Existing owned rows are preserved under the same uid/API key across login lifetimes. A stale service cannot erase them or read them into an obsolete actor; a new owned service can restore accepted job IDs. No queue row migration or deletion was introduced.

An accepted server upload may finish after its old actor is invalidated. The old response is not applied to that actor. The original queued capture and stable session ID remain available; a subsequent owned retry can recover the same accepted job through the existing idempotent acceptance contract. A mocked accepted-response/retry test verifies that recovery without deleting the synthetic source file. This is not evidence of a live backend upload.

`ApiClient.refreshAccessToken` now accepts the same optional local session predicate, and the generic onError path passes its **original request's** guard into refresh. The predicate is checked before a refresh response commits tokens or expires a session, including A→B→A with identical credential bytes. A stale initiating refresh is not shared with a new valid epoch. A ticket prevents the old refresh's finally block from clearing the newer single-flight request; concurrent callers in the same valid epoch still share one refresh. No credential cache or new serialized network field was added.
