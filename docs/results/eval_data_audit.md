## 등급
- **verified (count)**: 세트 렙 수를 라벨과 독립된 신호 하나 이상으로 다시 셌고 같았다.
- **verified (intervals)**: 렙마다의 구간(시작·끝 프레임)까지 독립 신호로 맞았다.
- **unverified**: 라벨을 독립적으로 확인할 방법이 없거나 확인하지 않았다.
- **suspect**: 독립 신호와 어긋난다.

### 1.2 자른 클립이 원본과 같은 프레임인가 (Home `clips/align_*.json`)
- 방법: 원본을 처음부터 디코드해 프레임 번호로 고른 64×36 회색 축소본과, 클립의 축소본을 프레임마다 비교(오프셋 −6…+6 중 차이가 가장 작은 것).
- 결과(검증 18세트, 세 가지 클립):

| 클립 | 만든 곳 | 프레임 수 = 설계(e−s+135) | 프레임별 최선 오프셋 0 | 세트별 중앙값 |
|---|---|---|---|---|
| `ref_exact`(기준: 원본에서 프레임 번호로 잘라 crf 10) | Home | 18/18 | 99.9% | 0 (18/18) |
| `mac_http_ff812`(D-T3-18과 같은 절차: Mac ffmpeg 8.1.2, x264 core 165 r3222, Zenodo HTTP) | Mac | 18/18 | 96.0% | 0 (18/18) |
| `home_http_ff902`(halpe-w20s3와 같은 절차: Home ffmpeg 9.0.2, x264 core 164 r3095, Zenodo HTTP) | Home | 18/18 | 96.1% | 0 (18/18) |

- 0이 아닌 프레임(약 4%)은 거의 움직임 없는 프레임에서 생긴다(1·2위 차이가 20% 안인 "모호" 프레임 47–278개/세트).
- `cut()`의 입력 탐색은 이 원본(CFR)에서 프레임 단위로 정확했다. fps 변환, 크기 변환, 타임스탬프 오차는 없다.
- Zenodo HTTP 읽기에서 "Stream ends prematurely" 경고가 여러 번 났지만(파일 끝부분) 만들어진 클립 18개는 모두 설계 길이였다. 다만 `cut()`은 ffmpeg 종료 코드만 보고 프레임 수를 확인하지 않는다. D-T3-18 때 w13_s2가 262바이트로 남은 적이 있다(진행 기록 2026-10-17).

### 1.3 라벨 프레임 번호와 영상 프레임 번호가 같은가 (Home `ana/pose2d_offset_*.json`)
- MM-Fit zip의 `wXX_pose_2d.npy`(저자 제공 2D 포즈, OpenPose COCO-18 순서 — 목 = 두 어깨 중점으로 확인)는 라벨과 같은 프레임 번호를 쓴다(센서 파일도 같은 번호 열을 가짐).
- 우리 m COCO17 키포인트(어깨·팔꿈치·손목 평균, 신뢰도 ≥ 0.5)를 클립 프레임 k = 영상 a+k에서 구하고, 저자 포즈의 프레임 a+k+d와의 거리 중앙값이 가장 작은 d를 찾았다(d = 0이면 라벨 프레임 n = 영상 프레임 n).

| 세션 | 세트별 d (m COCO17 / m Halpe26) | d에서 거리 | d = 0에서 거리 |
|---|---|---|---|
| w00, w05, w12, w13 (12세트) | 0 / 0 | 2.0–6.9 px | 같음 |
| w19 | s1 −23 / −24, s2 −22 / −23, s3 −15 / −16 | 4.1–8.9 px | 10.6–26.7 px |
| w20 | s1 +17 / +17, s2 +21 / +22, s3 +26 / – | 3.5–4.4 px | 27.8–32.6 px |

- **w19·w20은 라벨 프레임 번호가 영상 프레임 번호와 0.5–0.9초 어긋난다.** w20은 세션 안에서 +17 → +26으로 커진다(시계 드리프트로 보임, 추정). w19 영상은 52,561프레임(0–52,560)인데 저자 포즈 마지막 번호가 52,561이라는 것도 같은 방향이다.
- 영향:
  - **렙 수 채점에는 영향이 없다**(추정이 아니라 확인): 클립이 세트 전체를 덮는다. w20은 클립이 라벨 프레임 s−64…e+70, w19는 s−113…e+21을 덮는다. 저자 포즈의 첫 저점은 라벨 시작 뒤 15–26프레임, 마지막 저점은 라벨 끝 전 19–61프레임이다.
  - **"클립 90프레임 = 라벨 시작"을 쓰는 모든 구간 해석은 w19·w20에서 틀린다.** 예: halpe_w20s3.md의 "w20_s3 라벨 구간 클립 90–818"은 실제로 약 64–792다.
- 조정 9명은 영상 원본을 받지 않아 확인하지 못했다(미확인).

### 1.4 렙 수 교차 확인 (Home `mmfit_label_audit/result.json`)
- 저자 2D 포즈: 손목 y − 어깨 y(두 쪽 평균) → 9프레임 평균 → 세트 구간 p5–p95로 정규화 → 0.35/0.65 슈미트 저점(Exercise3D 정답과 같은 카운터).
- 귀(eb_l)·폰(sp_r)·시계(sw_l) 가속도: 세트 구간 크기 신호의 자기상관 주기(0.8–4 s) → 길이 ÷ 주기.

| | 2D 포즈 = 라벨 | 귀 IMU ±1 | 폰 IMU ±1 | 앞 3 s / 뒤 1.5 s 패딩에 렙 모양 저점 |
|---|---|---|---|---|
| 검증 18 | **18/18** | 14/18 | 15/18 | 0 / 0 |
| 조정 47 | 46/47(w17_s3: 라벨 9, 포즈 8) | 45/47 | 47/47 | 1(w17_s2 앞) / 0 |

- IMU가 어긋난 세트는 대부분 주기의 2배·절반을 잡은 경우다(w19 무릎 푸시업 s2 ≈ 20, w00_s1·s2 시계 ≈ 5.6). w19_s3(라벨 7)은 IMU가 11–13, 2D 포즈는 7 → 2D 포즈 쪽을 따른다.
- 2D 포즈는 같은 영상에서 저자가 뽑은 자동 추정이라 정답은 아니다. 그래도 우리 파이프라인·라벨과 독립된 두 번째 신호(IMU)와 함께 맞으므로 렙 수는 **verified (count)**로 둔다. 렙별 구간은 라벨에 없어 확인할 대상이 없다.
- 프레임 시계(프레임 번호 ÷ 센서 유닉스 시각): 대부분 30.0, w13 세트는 28.0–28.6, 조정의 w02_s3·w03_s1·w04_s2·w08_s1(26.8)·w10_s1은 26.8–29.4. 영상은 CFR 30이므로 이 세션들은 실제보다 4–11% 빨리 재생된다(앱의 프레임 수 기준 규칙이 보는 속도가 다름, 영향 미측정).

### 1.5 평가 코드 해석
- off-by-one: 클립 길이와 프레임 0 위치는 설계대로다(1.2). `clip_offset_frames = round(min(90, s))`도 맞다.
- 단위: 라벨은 프레임, 자르기는 초(÷30). 원본이 CFR 30이라 맞다.
- 채점 창: 렙은 클립 전체에서 센다(라벨 밖 4.5 s 포함). 1.4에서 패딩에 진짜 렙 모양 움직임은 65세트 중 1개뿐이므로, 패딩에서 센 렙은 "추가"로 보는 것이 맞다.
- 세트 단위 비교라 같은 세트에서 하나 놓치고 하나 더 세면 정확도에 안 나타난다(렙 구간 라벨이 없어 고칠 수 없음).
- `cut()`은 자른 결과의 프레임 수를 확인하지 않는다(1.2).

## 2. 공개 데이터 (Mendeley 7운동 + YouTube CC, D-DATA-01)
- 라벨: Claude 서브에이전트 두 개가 3 fps 접촉 시트를 독립으로 보고 셈. 렙 수가 정확히 같을 때만 `rep_status = ok`(Mendeley 290/411 비중복, YouTube 96/133). 사람 검수 없음. 두 라벨러가 같은 시트를 봐서 오류가 서로 독립이라고 보기 어렵다(추정).
- 렙 확신도: Mendeley ok 세트 중 한 쪽이라도 `low`가 75/290, YouTube 15/96. 검증 측면 푸시업 22세트 중 `low|low` 2개.
- `partial`(클립 시작·끝에 걸린 렙): Mendeley ok 세트의 191/290(66%), YouTube 32/96가 0이 아니다. 엄격 채점은 이 렙을 앱이 세면 "추가"로 친다. 결과가 이 규칙에 민감하다.
- Mendeley는 15 fps 원본을 프레임 복제로 30 fps로 바꿨다(새 정보 없음, 앱의 시간 규칙은 같은 동작을 두 배 프레임으로 봄).
- 숫자로 교차 확인할 독립 신호(IMU, 모캡)가 없다. 렙 구간은 `rep_times`(3 fps 타일 시각)뿐이고 채점에 쓰지 않는다.
- 등급: **unverified (count)**. 검증 세트 숫자는 "AI 라벨과의 일치"로 읽어야 한다.

## 3. Exercise3D
- 라벨: `outputs/exercise3d_labels/<seq>/geometry/canonical_3d.npz`(Sapiens2-5B 2D, 3캠 가중 삼각측량, `not_ground_truth: true`). 렙 수와 저점 프레임은 `outputs/rep_validation/gt_and_view.py`가 3D 높이 신호의 주기로 자동 계산.
- 안정성: 임계값 0.25/0.75, 0.45/0.55로 바꿔도 13/13 같은 렙 수. NaN 라벨 프레임은 barbellrow_0003 꼬리 64프레임뿐.
- 프레임: 영상 프레임 수가 라벨보다 1 많은 캠이 5개(pushup_0000·0001·0004, squat_0001 cam1·3, barbellrow_0002 cam3), 나머지 같음. 캠 간 동기 오차 ≈ 16 ms(타이밍 불확실성 18.8 ms, pushup_0001 메타데이터).
- 채점 코드(`analyze.py match`): 렙 끝 프레임이 "그 프레임 + 5 이전의 아직 안 쓴 **가장 늦은** 저점"을 가져간다. 그래서 렙 끝이 다음 저점 5프레임 앞에 오면 중간 저점을 건너뛰고 놓침+추가가 같이 생길 수 있다(코드 그대로 두고 `ex3d_score.py`에 이 동작을 테스트로 적음).
- 분할 오염: D-B-03 재확인 임계값은 검증 피험자 P2 영상(squat_0002, barbellrow_0003)을 보고 정했다(decisions.md D-B-03). P2·P3 "검증" 수치는 재확인 규칙에 대해 독립이 아니다.
- 등급: **unverified**(자동 의사 정답). 렙 수는 안정적이지만 독립 신호로 확인한 것은 아니다.

## 4. Fit3D rep_ann (Home `fit3d_repann_audit/result.json`)
- 라벨: `train/<s>/rep_ann.json`, 운동마다 경계 프레임 목록(50 fps). 정답 렙 수 = 경계 수 − 1(D-T3-17).
- 확인: 모캡 `joints3d_25`로 스쿼트 = 골반 높이, 푸시업 = 어깨 중점 높이, 로우 = 손목–어깨 거리(위쪽 = 카메라 y축 평균), 9프레임 평균, 슈미트 저점.
  - 24/24 세트에서 경계 사이마다 저점이 **정확히 1개**.
  - 경계 밖(앞뒤)에 세트 구간 기준으로 렙 모양 저점 0.
  - 영상 프레임 수 = 모캡 길이 + 0–2.
- 등급: **verified (intervals)**(모캡 기준). 앱은 영상 전체를 세므로, D-T3-18의 Fit3D "추가" 렙(검증 +30–38)은 라벨 누락 때문이 아니다.

## 5. 이 감사로 바뀌는 해석
- MM-Fit 18세트는 렙 **수** 기준으로 믿을 만하다. 다만 이 세트들은 이제 dev/진단용이다(사용자 지시).
- w19·w20 구간 해석(라벨 시작 = 클립 90)은 쓰지 않는다. 필요하면 1.3의 d로 고친다.
- 공개 데이터 수치는 "AI 2패스 라벨 기준"이라고 적어야 한다. Exercise3D는 "Sapiens 의사 정답 기준"이라고 적어야 한다.
