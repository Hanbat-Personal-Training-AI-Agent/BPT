# lift-compare 사전 등록 계획 — 2D 모델(COCO17 vs Halpe26)이 3D(MotionAGFormer-XS)에 주는 영향

**상태: 제안, 미승인.** 2026-10-19, 브랜치 `ai/lift-compare`(integration/ai c113150 위). 결과를 보기 전에 이 파일을 커밋한다. 이 파일에 적은 규칙으로만 "차이 있음/없음"을 말한다. 모델 채택·기각, 앱 변경, 병합, 새 학습은 하지 않는다.

## 0. 변경 이력 (결과를 보기 전)
- v1(최초 지시): 3D 각도·MPJPE를 COCO17 / Halpe26(a: COCO 부분집합, b: Halpe 고유 머리·목·엉덩이) × 원래 XS / Fit3D 미세조정 XS로, 실험 A(같은 상자)·B(앱 경로) 분리.
- v2(코디네이터 추가 지시 4건, 같은 날, 결과 전): 목표 = 온디바이스 3D 개인 트레이너, 3D는 항상 켬. 렙 카운트는 선택 기준 아님(부록). 주 비교 = 파이프라인 A(m COCO17 → XS) vs B(m Halpe26 → COCO17 부분 → H36M17 → XS, 즉 변형 a), 변형 b는 부차. 2D 정확도·안정성, 3D(MPJPE, P-MPJPE, 관절별 위치 오차, 각도, ROM, 떨림, 시점별), 입력 분포 이동, 학습 설정과 좌표·정규화 일치 확인, 제약(관절 각 한계·뼈 길이) 적용 전/후, 손목 출처(rtmpose vs MediaPipe 손 교체), Fit3D 각도 분포·뼈 길이 비 통계(ai/lift-app용), D-D-01..07 재감사.

## 1. 질문
1. (Q3, 주) 같은 XS에 m COCO17 2D와 m Halpe26 2D(변형 a)를 넣었을 때 3D 정확도가 달라지는가, 어느 쪽으로, 잡음보다 큰가.
2. (Q2) 원래 H36M XS vs Fit3D 미세조정 XS — 증거만.
3. 변형 b(Halpe 고유 관절), 손목 출처, 정규화, 제약은 부차 질문.

## 2. 데이터와 정답 등급

| 3D 평가 불가 | 공개(Mendeley·YouTube), MM-Fit | 3D 수치 없음 |

- 시점(영상별 수평 시점각, `view_and_side`): 측면 ≤40°, 사선 40–75°, 정면 ≥75°. **Fit3D 카메라는 모두 약 56–75°(정면 75–90°는 푸시업 1영상 정도)** → Fit3D로 측면은 **평가 불가**, 정면은 영상 수가 적으면 그대로 적고 판단에 쓰지 않음.
- Fit3D 50 fps → 앱 30 fps로 골라냄(D-D와 같음: `round(arange(0, n, 50/30))`).
- Fit3D 라이선스: Home에서만 처리(reacquire 문서의 "Fit3D는 Home에만" 지시를 따름). 영상·프레임·좌표는 저장소에 넣지 않고 집계값만 문서에. 이미지는 Read로 열지 않음.

## 3. 비교 변수
### 3.1 2D 모델 (Home PyTorch, mmpose 1.3.2, top-down)
- m COCO17: `rtmpose-m_8xb256-420e_coco-256x192.py` + `rtmpose-m_simcc-coco_pt-aic-coco_420e-256x192-d8dd5ca4`(sha256 929f00f2…, 앱 `rtmpose_m_forward`의 원본).
- m Halpe26: `rtmpose-m_8xb512-700e_body8-halpe26-256x192.py` + `…halpe26_700e-256x192-4d3e73dd`(sha256 4d3e73dd…, `~/bpt-models/rtmpose_m_halpe26_forward.mlpackage`의 원본).
- 앱은 Core ML이고 여기는 PyTorch → 실험 A는 "모델 가중치 차이"를 재는 것이고 Core ML 변환 오차는 포함하지 않음(문서에 명시).

### 3.2 실험 A(주): 같은 상자
- 상자: 프레임마다 RTMDet-m COCO(`rtmdet_m_8xb32-300e_coco_20220719_112220-229f527c`)의 사람 검출 중 점수×넓이 최대(Fit3D는 한 사람), 점수 ≥ 0.2. 두 모델에 **같은 상자**를 줌(mmpose 기본 상자 → 아핀 변환, 두 모델 같은 코드).
- 상자 검증: 투영 모캡의 팔다리·어깨 12점이 상자 안에 있는 프레임 비율 ≥ 99%, 상자 없는 프레임 ≤ 1%인 영상만 실험 A에 씀. 나머지는 개수와 이유를 적고 제외.
- 실험 B(앱 경로 pose-replay, cur/lb/s15/det): **Fit3D는 Mac으로 옮기지 않으므로 측정 안 함**. Exercise3D에서는 reacquire 트랙이 이미 만든 Mac pose-replay CSV(`~/bpt-runs/reacquire/e3d__{cur,lb,s15,det}`)를 그대로 올려 [E3D·의사 정답] 등급으로만 봄. A와 B는 한 주장에 섞지 않음.

### 3.3 2D → H36M17 매핑(XS 입력)
- **COCO17(파이프라인 A)**: 앱과 같은 `coco17_to_motionagformer_h36m17`(Python)·`PoseCoordinateTransforms.coco17ToH36M17`(Swift) — 골반 = 두 엉덩이 중점, 흉곽 = 두 어깨 중점, 척추 = 골반·흉곽 중점, 9 = 코·흉곽 중점, 머리 = 두 눈 중점, 팔다리는 그대로. 신뢰도도 같은 규칙.
- **Halpe26 변형 a(파이프라인 B, 주)**: Halpe26 0–16(COCO17과 같은 순서)만 떼어 위와 같은 함수. 지금 앱이 Halpe26에서 하는 것과 같음(17–19는 버리고 발만 씀).
- **Halpe26 변형 b(부차, 실험일 뿐 앱 변경 아님)**: 골반 ← Halpe 19 "Hip", 흉곽 ← 18 "Neck", 머리 ← 17 "Head", 척추 = 새 골반·새 흉곽 중점, 9 = 코·새 흉곽 중점, 나머지는 a와 같음. 신뢰도는 해당 관절의 신뢰도(중점은 평균).

### 3.4 손목 출처(COCO17, 변형 a에만)
- `rtmpose`: 그대로. `mediapipe`: `scripts/compare_person_crop_rtmpose_motionagformer.py`의 `run_hand_stage`와 같은 규칙(손목 crop 한 변 = 0.15 × 사람 키, MediaPipe Hand Landmarker VIDEO 모드 양손 따로, `hand_landmarker.task`(앱 번들과 같은 파일), 반대쪽 RTMPose 손목에 더 가까운 MediaPipe 손목은 버림, `build_motionagformer_input_2d(wrist_source="mediapipe")`). 신뢰도는 RTMPose 값 유지(모듈 규칙). ai/lift-app의 Swift 연결과 정의가 다르면 문서에 차이를 적음.

### 3.5 정규화(XS 입력 좌표)
- `person_crop`(앱 기본, D-12; 미세조정 XS의 학습 설정): `PersonSquareCropTracker`(여백 2.0, 히스테리시스) → (p − 중심) / 한 변 × 2.
- `screen`(원래 XS의 학습 설정): MotionAGFormer `data/reader/h36m.py`처럼 전체 프레임 `X / w × 2 − [1, h/w]`. Fit3D 900×900, H36M 1000×1000(같은 연구실·비슷한 카메라 배치) → 원래 XS에는 이것이 "학습과 같은 입력". 출력 3D는 같은 단위(깊이 = z/w×2).
- 두 정규화 모두 잼. 원래 XS의 주 결과는 **둘 다 표에 싣고**, 판정은 각각 따로 함(섞지 않음).
- 3D 출력 → 미터: 정답 골반 깊이로 약원근 환산(D-D-07과 같은 "정답 크기 힌트", 모든 변형에 같게 적용). P-MPJPE는 크기를 다시 맞추므로 이 영향 없음.

### 3.6 리프터
- 원래 XS: `motionagformer-xs-h36m.pth.tr`(sha256 7abb32ea…), 27프레임 창, lookahead 5, 앱과 같은 선택 행(`app_predict`).
- Fit3D 미세조정 XS(D-D-06/07): **가중치가 남아 있지 않음**(D-D-07 정리에서 "체크포인트 측정 후 삭제", Mac·Home 전체 검색에서 없음 확인). 새 학습 금지 → **측정 불가**로 적고, 같은 레시피 재생성은 사용자 승인 항목(G)으로 올림.

### 3.7 제약(관절 각 한계 + 뼈 길이)
- ai/lift-app이 만드는 Python 기준 구현이 이 트랙 마감 때 그 브랜치에 있으면 그 커밋을 고정해 raw와 제약 적용 결과를 같은 지표로 잰다. 없으면 **측정 안 함**.
- 제약에 쓸 통계(§6)는 이 트랙이 Fit3D에서 계산해 제공. 평가 누출을 막기 위해 **평가에 쓰는 제약 통계는 조정 피험자 s03–s05에서만** 계산(검증 s07–s11 제외), 전체 피험자 버전은 따로 표시.

## 4. 지표 (ai/lift-app과 공유하는 정의)
- **MPJPE**(mm): 예측·정답 모두 골반(0번) 기준, 17관절 평균 유클리드 거리, 프레임 평균. **P-MPJPE**(mm): 프레임마다 닮음 변환(회전·크기·이동) 정렬 후 같은 평균.
- **관절별 3D 위치 오차**(mm): 골반 기준 관절별 평균(손목·팔꿈치 포함).
- **가속도 오차**(mm/프레임², 30 fps): ‖Δ²P − Δ²G‖ 관절 평균.
- **각도**(°, 가까운 쪽 = 정답 기하로 정한 쪽 — 모델마다 바뀌지 않게): 무릎(엉덩이–무릎–발목), 엉덩이(어깨–엉덩이–무릎), 팔꿈치(어깨–팔꿈치–손목) 내각, 몸통 `trunk_g` = 엉덩이 중점→어깨 중점과 중력 위 방향의 각(정답 카메라 자세로 계산 = 기기 가속도계 가정), 참고로 `trunk_cam`(카메라 −y 기준).
- **렙 극값 오차**: Fit3D `rep_ann` 경계 사이 렙마다 무릎·엉덩이·팔꿈치는 최솟값, 몸통은 최댓값을 정답과 비교한 |차|. 중앙값과 p90(렙 단위).
- **ROM 오차**: 렙마다 (최댓값 − 최솟값) 예측 vs 정답의 |차|, 중앙값·p90.
- **각도 떨림**: |Δ²θ − Δ²θ정답| 중앙값(°/프레임²), 렙 안 프레임.
- **2D 오차**: 투영 정답과의 거리 ÷ 투영 정답 17관절 상자 긴 변, 관절별 평균과 PCK@0.05. 엉덩이는 부호 있는 오프셋(몸통 축 방향 ÷ 몸통 길이)으로만.
- **2D 떨림**: ‖Δ²K − Δ²K정답‖(px/프레임², 900 px 기준). **끊김**: 신뢰도 < 0.3 프레임 비율(관절별), 손목 MediaPipe 교체율.
- **입력 분포**: 모델별 신뢰도 분포(관절군별 중앙값·p10), 2D 뼈 길이 비(예측 ÷ 투영 정답: 허벅지·정강이·위팔·아래팔·어깨 폭·엉덩이 폭·몸통), XS 입력 공간에서의 사람 크기(정규화 후 골반→머리 거리 중앙값)를 `screen`·`person_crop`·투영 정답 각각.
- **손목 묶음**: 손목 2D 오차, 3D 손목·팔꿈치 위치 오차, 팔꿈치 각 렙 극값·프레임 오차, 손목 떨림 — 운동·시점별.

## 5. 비교 규칙(잡음과 차이 구별)
- 단위: 검증 피험자 5명. 각 지표의 **쌍 차이**(변형 a − COCO17, 같은 영상·같은 프레임)를 영상별로 구한 뒤 **피험자 묶음 부트스트랩**(피험자를 복원 추출, 2,000회, seed 0)으로 95% CI.
- "차이 있음" = CI가 0을 포함하지 않음 **그리고** |차이| ≥ 실용 문턱(MPJPE·P-MPJPE·관절 오차 2 mm, 각도 1°, 가속도 0.5 mm/프레임²). 아니면 "구별 불가"(같다는 증명 아님). 방향은 항상 적음.
- 피험자별 값도 표에 싣는다(5명 중 몇 명이 같은 방향인지).
- 운동별·시점별 칸은 영상 수와 함께, 영상 < 4이면 판단에 쓰지 않음.
- 여러 칸을 보므로 "어느 한 칸에서 차이"는 결론이 아니라 관찰로만 적고, 주 결론은 검증 전체 MPJPE·P-MPJPE·각도 렙 극값(4관절)로만.

## 6. ai/lift-app에 줄 통계(집계만)
- Fit3D 모캡 관절 각 분포: 무릎·팔꿈치·엉덩이(어깨–엉덩이–무릎)·몸통·어깨(팔–몸통) 등 p0.1, p1, p5, p50, p95, p99, p99.9 — 전체 운동(추출된 모든 `joints3d_25`), s03–s05 / 전체 피험자 따로.
- 뼈 길이(모캡은 피험자별 고정 골격) 비: 허벅지/정강이, 위팔/아래팔, 어깨 폭/엉덩이 폭, 몸통/허벅지 등, 피험자별 값과 범위.
- H36M 모캡: 이 기계들에 데이터 없음 → **측정 안 함**. SMPL은 비상업 라이선스라 쓰지 않음.

## 7. D-D-01..07 재감사
- 남아 있는 것으로 다시 만들 수 있는 수치만 재현 시도: 원래 XS + m COCO17의 검증 MPJPE 148 / P-MPJPE 89, 각도 렙 극값(D-D-07 결과 2). 이번 2D 경로(RTMDet 상자 + PyTorch)는 D-D-07(Mac pose-replay crop 추적 + Core ML)과 다르므로, 차이는 그 원인으로 증명될 때만 원인을 적고 아니면 "재현 불가(입력 경로 다름, 원래 CSV 삭제됨)"로 둠.
- 미세조정 XS 수치(D-D-06/07): 가중치 없음 → 재현 불가.

## 8. 하지 않는 것 / 평가 불가
- 앱 코드·번들·기본값·`enableMotion3DForCamera` 변경, 병합, 채택 판단, 새 학습·미세조정.
- 자세 오류 검출률: 틀린 자세 라벨 데이터 없음 → 평가 불가(필요 데이터: 사람이 라벨한 틀린 자세 영상 + 3D 정답).
- iPhone FPS·종단 지연: ai/lift-app 담당, 숫자가 오기 전까지 측정 안 함.
- 3D 기반 렙 카운트: 부록에서 기존 2D 결과(D-T3-20·21) 인용만, 새로 재지 않음.
