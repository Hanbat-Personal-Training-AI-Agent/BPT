# 인증된 심층분석 API 전송·실행 검증

2026-10-26. 이미 캘리브레이션에 사용·업로드한 사용자 IMG_9900을 재사용했다. 새 인물이나 데이터셋 영상을 업로드하지 않았다. 입력은 운동 세트가 아니며4개 임의 시간 구간은 **전송 계약 시험**이다. 생성된 각도·경고를 운동 정확도의 증거로 쓰지 않는다. 원본 영상·결과 영상·개인 관절·계정 비밀은 git에 넣지 않는다.

## 실제 검증 범위

기존 테스트 계정 로그인 → JWT 업로드 접수 → Bearer 없는 서명 PUT → 완료 접수 → 실제 L4 GVHMR 실행 → 리포트·영상 서명 GET을 실행했다. 로그인 정보는 Mac의 기존 private 파일에서 메모리로만 읽었다. 신규 계정 생성·JWT 우회·GPU 재시도는 하지 않았다.

같은 완료 요청 두 번 및 같은 세션 재접수가 같은 job을 가리키는지, 인증 없는 접수·조회401, 완료된 작업 재시도409, 반복 구간 보존, 현재 계정의 캘리브레이션 β 사용, 리포트 안정성, URL 갱신, 별도 저장소 요청에 인증 토큰을 보내지 않는지까지 확인했다. 이는 API 전송 E2E이며, iPhone 네이티브 운동 녹화부터 시작한 전체 운동 E2E와 구분한다.

## 성능 시험 입력과 기준

후속 `runtime-502d9ef-20261026`은 모델 입력·가중치를 유지하고 구간별 처리시간, 절대 GPU 사용량20ms 표본, worker 프로세스 재사용 표식만 추가했다. 같은20초 인코딩 영상을 반복해30.066667초902프레임 및60.000초1800프레임 입력을 만들었다.20·40초의 경계는 인위적 반복이다. 연속60초 실제 운동의 정확도 시험이 아니다.

원래 기준은 L4에서60초 영상 처리180초 이하(콜드 시작 제외), 메모리22GB 이하다. worker는 입력 검증·다운로드·분석·결과 업로드·임시 파일 정리까지 측정하며 최종 상태 커밋·플랫폼 시작·대기·클라이언트를 제외한다. runner 시간도 따로 제공한다. 메모리는22,000,000,000바이트로 보수적으로 비교하고 원래 MiB 값을 남긴다.20ms 사이 짧은 peak를 놓칠 수 있는 측정 한계가 있다.

30/60초 결과와 재사용 여부는 완료한 실행만 `summarize_authenticated_runs.py`로 집계했다. `instanceId` 일치는 같은 Python worker 프로세스 재사용 증거이며 플랫폼 전체 cold/warm 시작을 확정하지 않는다. 모델은 매 작업에서 다시 로드한다.

30초와60초 기본 실행은 같은 worker process의 작업 순서1·2였다.60초 기본 실행은 **180초 성능 기준 불합격**이다. runner만 따져도 기준을 초과하므로 플랫폼 시작이나 업로드 시간을 제외하는 방식으로 통과시킬 수 없다. 관측한 GPU 메모리는22GB 기준을 충족한다. 표본 사이 peak의 한계는 그대로 남는다.

60초 기본 실행의 runner 단계는 내부 정규화20.552초, 추적67.087초, ViTPose140.817초, HMR2 특징81.837초, GVHMR3.765초, 후처리4.748초였다. 추적·2D·특징 추출이 주요 시간 소비 구간이며, GVHMR 네트워크 시간만 제시하면 실제 처리 속도를 과장하게 된다.

CPU4 실험은 `Function.with_options(cpu=4)` 한 번으로 수행했고 배포 설정은 변경하지 않았다. Modal의 CPU request는 최소 할당과 관련되며 기본 실행도 여유 자원을 사용할 수 있으므로 기본값을 강제 상한으로 해석하지 않는다. [Modal 자원 문서](https://modal.com/docs/guide/resources). 다른 프로세스에서 각 조건1회만 실행한 결과이므로 CPU 수 자체가 느려짐의 원인이라고 확정할 수 없다. **이 실험에서는 개선을 관측하지 못했다.** 추가 GPU 재시도 없이 보존한 두 결과를 읽어 비교했다.

두60초 보고서는 수치적으로 동일하지 않았다. 비교한2854개 숫자 중2327개가 달랐고, `anglesDeg`100개 값의 최대 차이는2.929도였다. 임의3번째 구간의 bottom 선택은65프레임/2.167초 차이였으며 timeline 문구2개도 달랐다. 단위가 섞인 최대 차이65를65도 오차로 쓰지 않는다. 전체 `faults`와 `metricValidity` 레코드도 수치 근거·지지도를 포함하므로 완전히 같지 않았다. 이 입력에는 운동 정답이 없어 어느 실행이 더 정확한지 판정할 수 없다. 비결정적 추론 또는 극값 선택의 민감도 가능성은 별도 통제 실험이 필요한 가설이다.

최초 CPU 진단 파일의 `result=passed`는 작업 완료를 의미했으며 성능·정확도·수치 동일 통과가 아니었다. 재현 실행기는 `completed`와 별도 성능 기준으로 고쳤다. 원본 파일은 그대로 보존하고, 완료 결과만 조회하는 `--inspect-only`로 단위별 차이를 추가 검증했다.

비식별 집계는 [정량 JSON](deep_authenticated_flow_20261026.json)에 있다. 호출·입력·측정 범위를 분리했으며 계정·작업 ID·서명 URL·영상·개인 관절 값은 포함하지 않는다.
