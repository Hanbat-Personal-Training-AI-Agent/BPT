# geometry

## 뼈 길이 고정 (`bone_lengths.py`)

체형 캘리브레이션 결과(`boneLengthData.segments`, cm)를 MotionAGFormer-XS `selected3D`(H36M17 [17,3])의
팔다리 길이 제약으로 쓴다. Swift 구현은 `ios/Runner/NativePose/PosePipeline/BoneLengthConstraint.swift`,
두 구현은 `tests/fixtures/bone_length_cases.json`을 공유한다. 앱 3D 경로에는 아직 연결하지 않았다.

- MotionAGFormer 출력은 골반 기준 상대좌표이고 단위가 정규화 화면 좌표(metric 아님)라 비율만 쓴다.
  프레임마다 s = median(관측 길이 / 목표 cm)을 제약 대상 분절에서 구하고, 각 분절을 목표 × s로 맞춘다
  (`blend`로 관측 길이와 섞음, 1 = 완전 고정).
- 골반에서 바깥쪽으로 트리를 따라가며 자식 관절의 방향은 유지하고 하위 트리를 함께 옮긴다.
  제약하지 않는 분절은 관측 길이를 유지한 채 부모를 따라 이동한다. 골반은 움직이지 않는다.
- 기본 제약 분절은 허벅지·정강이·위팔·아래팔(좌우 8개). 몸통·머리 관절은 앱이 COCO 평균으로 합성하므로
  (`appDefinitionDiffers`) 로더가 버리고, 골반-엉덩이는 앱 골반이 COCO 엉덩이 점의 중점이라 SMPL 관절 중심과
  정의가 달라 기본에서 뺐다.
- 길이가 1e-6 미만인 분절은 `degenerate`로 표시하고 길이를 바꾸지 않는다. 쓸 수 있는 분절이 하나도 없으면
  입력을 그대로 돌려준다.
- **3D 경로 연결 시 순서: selected3D → 뼈 길이 고정 → 무릎 과신전 차단.**
  무릎 차단은 정강이를 회전만 하므로(길이 보존) 이 순서면 고정한 길이가 유지된다.

실데이터 점검(`scripts/check_bone_length_constraint.py`):

- 세로 영상(720×1280)에서는 발목의 정규화 y가 1을 넘는다(H36M 학습 범위 약 ±1). 모델 출력의 xy는 입력 2D와
  허벅지까지는 거의 같지만(비율 ≈1.0) 발목은 안쪽으로 눌려 정강이가 목표 비율보다 25~40% 짧다.
  그래서 정강이 보정량이 크다(서 있는 더미 영상 33~62%). 매핑이나 scale 문제가 아니라 모델 입력 분포 문제다.
- 정면 스쿼트(`squat_03`)는 모델이 낸 허벅지/정강이 비율 자체가 프레임마다 0.7~3.5로 흔들린다(관측 길이 CV 0.2~0.5).
- 길이를 고정해도 방향은 모델 출력 그대로이므로 관절각 정확도가 좋아진다는 보장은 없다.
- 보정 후 길이 변동은 프레임별 s의 변동과 같다(더미 CV 1.5~3.5%, 스쿼트 12.5%). 연결할 때 s를 클립 단위로
  고정하거나 평활하면 더 줄어든다.

## 무릎 과신전 차단 (`hinge_limit.py`)

MotionAGFormer-XS `selected3D`(H36M17 [17,3])에서 무릎이 해부학적으로 불가능한 방향으로
꺾인 출력만 자른다. Swift 구현은 `ios/Runner/NativePose/PosePipeline/KneeHingeLimit.swift`,
두 구현은 `tests/fixtures/knee_hinge_limit_cases.json`을 공유해 같은 출력을 내는지 확인한다.

- 다리마다 u = knee − hip, v = ankle − knee, a = (L hip − R hip)를 u에 수직인 평면에 사영·정규화.
- θ = atan2((u × v)·a, u·v). **θ > 0 정상 굽힘, θ < 0 과신전.**
- θ < −limit(기본 10°)이면 정강이를 무릎 중심·축 a로 돌려 θ = −limit에 맞춘다(ankle만 바뀜, 길이 보존).
  그 외에는 입력을 그대로 돌려준다.
- |u|, |v|, |L|이 너무 작거나, L이 u와 거의 평행하거나, v가 축 a와 거의 평행하면 θ를 정하지 않고
  `degenerate`로 표시하고 손대지 않는다.
- 3D 경로 연결 시 순서: selected3D → (뼈 길이 고정) → 무릎 차단.
- **보정은 기본 OFF, 감지는 항상 ON.** 비퇴화 다리의 θ < −limit이면 report에 `hyperextended`가 서고
  그 프레임은 "3D 불량"(`is_bad_3d` / Swift `Result.bad3D`)이다. 3D 기반 판단은 그 프레임에서 건너뛰고,
  앱은 세션 동안 개수를 센다(`FormWarningTracker.sessionBad3DFrames`, 디버그 빌드 `workout_form_logs/*.jsonl`).

### 부호 규약 근거

MotionAGFormer-XS 출력은 y가 아래(이미지 좌표계), 골반 L−R은 +x 쪽이다. 서 있는 자세 위주의
캘리브레이션 영상 6개(4,598프레임)에서 이 규약의 θ 중앙값은 다리 모두 +4°~+15°, 보정 비율 ≤0.74%다.
부호를 뒤집으면 같은 프레임의 31~90%가 과신전으로 잡히므로 현재 부호가 맞다.
합성 테스트(오른손 좌표계, x=왼쪽, y=위, z=앞)에서도 굽힘 = θ > 0이다.

### 알려진 한계 (실데이터 점검 결과)

- 정면 스쿼트(`squat_03`)에서 MotionAGFormer가 깊이를 거의 평면으로 내보내 무릎이 정면 평면에서
  꺾인다. 굽힘 평면 법선과 축 a가 거의 수직(정렬도 중앙값 0.1~0.4)이라 θ 부호가 사실상 임의다.
  오른다리 92% 프레임이 보정 대상이 된다.
- 회전이 많은 영상(`sample_video`, 피겨)에서도 23%가 보정 대상이고 보정량이 평균 50°, 최대 169°다.
- 위 squat_03 92%는 세로 영상 입력 normalization(`screen`, y가 ±1.78) 때문에 다리가 눌린 출력에서 나온 값이다.
  3D 입력 기본값을 `person_crop`으로 바꾼 뒤(docs/research/rtmpose_motionagformer_image_to_pose_pipeline.md §13.1)
  squat_03 보정 비율은 오른다리 0%, 왼다리 0%이고, 세로 캘리브레이션 더미 4개도 0%다. 기본값 OFF는 그대로 둔다.
- 따라서 기본값은 OFF(`enabled=False`)이고, 이 축 정의로는 앱 3D 경로에 그대로 켜면 안 된다. 축 정의 보강(예: 정렬도가 낮으면
  degenerate 처리, 큰 보정량은 신뢰하지 않기)이 먼저다.

## 팔꿈치는 하지 않는 이유

팔꿈치도 경첩 관절이지만 H36M17의 어깨·팔꿈치·손목 3점만으로는 상완의 회전(내·외회전)을 알 수 없다.
무릎은 골반 좌우축이 굽힘축의 기준이 되지만, 어깨는 가동 범위가 커서 상완이 어느 방향으로 돌아가 있든
같은 3점이 나오고, 따라서 굽힘 방향의 부호를 정할 기준축이 없다.
후속 과제: 손 랜드마크(손바닥 법선 방향)를 결합하면 전완의 회전을 알 수 있어 부호를 정할 수 있을지 검토.
